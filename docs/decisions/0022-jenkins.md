# ADR 0022: Jenkins pipeline
- Status: accepted · Date: 2026-10-26
## Context
Jenkins is the CI tool most Spring Boot job descriptions name. GitHub Actions (`ci.yml`) already builds and tests every push. The aim here is a pipeline that does the same and more (the real-stack Playwright smoke test, which only existed as a local script), and that is itself code: anyone can start it with one command.
## Decision
- **Jenkins runs in a container on Docker Desktop**, built from `jenkins/Dockerfile` (JDK 21, Node 22, Docker CLI and compose, Chromium for Playwright). Plugins are listed in `plugins.txt`; the admin user, the anonymous read-only view and the `payledger` job are defined in `jenkins.yaml` (Configuration as Code and a Job DSL script). Nothing is set up by clicking. Start it with `docker compose -f jenkins/docker-compose.yml --env-file .env up -d --build`; UI on http://localhost:8090 (bound to localhost).
- **Docker-outside-of-Docker**: the host's Docker socket is mounted, so Testcontainers and `docker compose` start sibling containers on Docker Desktop. Docker-in-Docker was rejected (privileged, slow, a second image cache). The cost: access to the socket is root-equivalent on the Docker VM, so the Jenkins container runs as root and must stay local; a shared Jenkins would use rootless build agents instead.
- **Same path inside and outside.** `docker compose` run in Jenkins sends bind-mount paths (for example `./ops/postgres/init.sh`) to the host's Docker, which cannot see Jenkins' filesystem. The workspace root is therefore a host folder (`C:\jenkins-work`) mounted at `/c/jenkins-work`, which is also how Docker Desktop names that folder, and Jenkins is told to use it (`jenkins.model.Jenkins.workspacesDir`). Testcontainers needs `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal`, and `ops/ui/smoke.sh` takes `STACK_HOST` for the same reason: published ports are on the host, not in the Jenkins container.
- **Pipeline** (`Jenkinsfile`, declarative): Prepare (a throwaway `.env` with random values from `ops/ci/make-env.sh`, so no secret is stored in Jenkins or the repo), then Backend (`./mvnw verify`, JUnit report) in parallel with Admin UI (`npm ci`, type-check, build), then Stack smoke (`ops/ui/smoke.sh`, which starts the compose stack in its own project and runs Playwright with Chromium). Post: stack torn down, workspace cleaned. 45 minute timeout, no concurrent builds, last 10 builds kept.
- **Trigger: poll the repository every 5 minutes**, because a laptop has no public URL for a GitHub webhook. Repository and branch come from `PAYLEDGER_REPO` and `PAYLEDGER_BRANCH` (defaults: GitHub, main) so a pipeline change can be tried on a local copy first.
- **`ci.yml` stays.** A Jenkins on a laptop gives GitHub no visible check. When Jenkins runs on the cloud VM (M10) the workflow can be retired.
## Consequences
First build is slow (images, plugins, Maven and npm downloads); a full run is about 19 minutes, mostly the backend tests (about 14 minutes inside Docker Desktop's 8 GB VM) and the stack smoke (about 4 minutes). The pipeline needs Docker Desktop running. Playwright's dependency installer does not support Jenkins' base image (Debian 13), so the Chromium libraries are listed by hand in the Dockerfile.
## Findings from the first runs
The first Jenkins run found a real flaw in my smoke test: it asserted a payer wallet's balance while the ledger consumer was still posting a capture from the same test, so on a slower machine the balance was already 90.00. The check now uses a wallet no payment touches. A deliberately failing test showed a red build within about 90 seconds with the failure in the JUnit report.
## Alternatives rejected
Jenkins directly on Windows (not reproducible, not what a team would run); agents per stage in Docker (more plugins and the same path problem); storing secrets as Jenkins credentials (nothing here needs a real secret); a webhook through a tunnel (extra moving part for a demo).
