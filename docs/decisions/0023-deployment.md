# ADR 0023: Public deployment on one VM with Compose and Caddy
- Status: accepted · Date: 2026-10-27
## Context
M10 asks for a public demo. The stack is Postgres, Kafka, four Spring Boot services, an nginx-served UI, Prometheus, Grafana and Jaeger: about 4-5 GB of memory once running. AWS's free plan only offers 1 GB machines, which cannot hold it. Oracle Cloud's Always Free tier gives an Arm VM with up to 4 cores and 24 GB at no cost. A public address means strangers can reach it, so what is exposed matters more than how it is deployed.
## Decision
- **One VM, Docker Compose** (the same `docker-compose.yml` used locally plus `deploy/docker-compose.prod.yml`). No Kubernetes and no managed database or Kafka: for a demo they add cost and moving parts without showing anything the design does not already show. Images are built on the VM, so the same files work on Arm or x86.
- **Only Caddy is public** (ports 80 and 443). The overlay removes every other published port: the database, Kafka, the services with their actuator endpoints, Prometheus and Jaeger are reachable only inside the Docker network. Caddy gets and renews a Let's Encrypt certificate by itself and serves `/` (the console, whose nginx forwards `/api/*` and answers 404 for actuator and the mock bank) and `/grafana/` (read-only dashboards).
- **No domain to buy:** the host name is the dashed public IP under `sslip.io` (for example `203-0-113-7.sslip.io`), which resolves to that IP. A reserved public IP keeps the name stable across a stop and start. If Let's Encrypt refuses (shared rate limits), a free DuckDNS name is the fallback.
- **What a stranger can do:** log in as the published `demo` MERCHANT (sees and operates only its own payments, 30 payments a minute), and view Grafana. The ADMIN account, whose password exists only in `.env` on the VM, is not published; the video shows the admin screens. A demo payer wallet holds play money, nothing real is stored.
- **Client addresses behind two proxies.** The login rate limit counts per client address. Behind Caddy and nginx every request came from a proxy, so all visitors would have shared one limit of 10 logins a minute. auth-service now uses `forward-headers-strategy: native` (Tomcat's remote-IP handling, which only believes proxies on private networks), nginx appends the caller's address, and a test proves that two clients behind one proxy are counted separately.
- **Secrets** are random values written into `.env` on the VM by `deploy/provision.sh` (it reuses `ops/ci/make-env.sh`); nothing is in the repository, in CI, or in Jenkins. SSH is limited to the owner's address by the cloud firewall; the private key stays on the owner's machine.
- **Deployments are manual** (`deploy/deploy.sh`: pull, build, restart). Automatic deployment from CI would need an SSH key stored in GitHub or Jenkins; not worth it for a demo.
- **Smoke check from outside:** `ops/deploy/smoke-remote.sh` verifies valid HTTPS, the console, a real payment with the demo login, that actuator, the mock bank and every internal port are not reachable, and that the dashboard loads without a login.
## Consequences
No backups and no high availability: the VM is a single point of failure and `docker compose down -v` deletes the data, acceptable for demo data. Oracle may reclaim Always Free instances that stay idle for a week. A public demo login can be abused within the rate limits (spam payments for play money); the instance can be stopped at any time. The first build on the VM takes about 15-20 minutes.
## Alternatives rejected
AWS (free plan too small, paid instance for a demo); Kubernetes or ECS (cost and complexity for one VM's worth of load); publishing Grafana or the console directly on separate ports (more public surface, no TLS); a shared demo admin login (the admin can freeze accounts and replay dead letters).
